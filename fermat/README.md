# A Turing machine for Fermat's Last Theorem

**Current best: `machines/fermat_90.txt`, a 90-state, 2-symbol Turing machine**
(in the named-state format of bbchallenge's `weak_Collatz_conjecture_124_2.txt`).
Started on a blank tape, it **halts iff Fermat's Last Theorem is false**: it
searches for `x^E + y^E = z^E` with `E >= 3` and `x, y, z >= 1`, and runs forever
otherwise. Lean proves this (`TM.Fermat.M90.halts_iff`). Nothing in the construction uses
Wiles' proof. `RECORDS.md` lists every machine with its state count and Lean theorem. `PROOF.md`
walks through the proof in plain words.

The 90-state machine is obtained in two stages:

1. `fermat.txt` is the readable **127-state design**, generated by `build.py`.
   The Lean proof is written for this machine (`TM.Fermat.halts_iff`).
2. `minimize.py` merges states of the design that never disagree on a transition
   the run actually uses (an exact SAT search), giving 90 states. The proof
   carries over automatically (see "Smaller machines" below).
   `machines/fermat_90_annotated.txt` is the 90-state machine with each state
   named after the roles it plays in the design, and every transition commented.

For comparison, Randels' thesis *Studies in Turing Machines* (1965, pp. 81–82)
estimated that fewer than 400 states would suffice, without building the machine.

(A search can only halt when it finds a counterexample. So "halts iff FLT is
false" is the version that does not depend on FLT being true. Any machine
that always halts "halts iff FLT is true", but showing that needs Wiles.)

## How it works

Tape layout (blocks of 1s separated by `00`; a block of length `v+2` stores `v`, except A and R):

    B1=E 00 B2=x 00 B3=y 00 B4=z 00 M 00 A 0 R 0 Q

* **Enumeration.** `(B1..B4)` steps through every composition of every total in
  NEXCOM order (Nijenhuis–Wilf). Each step is made of local separator moves.
  B1 has minimum value 3, so every `(E>=3, x, y, z)` is eventually visited.
* **Cursors.** A "hole" is a single 0 inside a block, used as a loop counter.
  Two-state parsers ("find the next single 0 to the left/right") handle all
  navigation; they count 0s modulo 2, so a run of three 0s is also a hole. B1 always
  holds one: the exponent cursor, on cell 1 (the anchor) between powers and on cells
  `1 .. E+1` during a power (on the last cell it sits next to the separator). The base
  being powered carries a **marker** hole on its cell 1, and during a round a cursor
  on cells `3 .. β+1`.
* **R's hole is the gap after A.** A and R are separated by a single 0, and that 0 is
  the hole every parser that goes to R stops at; R itself is just `r` cells for the
  value `r`. Q follows R after another single 0, which no parser ever crosses.
* **Powers.** `R := 1`. Then a power starts with an exponent step from the anchor:
  for each of the E rounds, copy R `β−1` times onto Q and merge Q into R. A copy
  punches a cursor on R's first cell and moves it one cell per copied cell (it may
  reach R's last cell); R's hole stays put, so the way back is a scan to it. The
  merge fills the 0 before Q and erases Q's last cell. This gives `R = β^E`.
* **Accumulate and compare.** After a power the marker moves to the next base
  block, and R is added into A: the 0 between them is filled, a 1 is written past
  R's end and the cell before it is erased, which leaves `A + r` and a new `R = 1`.
  After `z^E` the marker would land on `M`: A (`1 + x^E + y^E` cells) and R (`z^E`)
  are erased one cell at a time, from A's right and R's left. The machine halts iff
  R runs out with exactly one cell of A left. Otherwise it clears the rest, writes A
  empty and `R = 1`, and moves to the next tuple.
* **Setup.** The anchor plays the marker of a "next base" step: the marker goes
  on B2 and the empty A becomes `A = 1` (the `1` of `R = 1`); with A empty, the
  separator after M and the 0 before R make three 0s, still a hole.

The search starts from the tuple (4,1,1,1), written by a 24-cell seed.

State budget of the 127-state design: seed 24, enumeration 43, setup 1, powers 31,
next base and adding into A 10, compare 9, clear and restore 9 (with `HE`). After
merging, every seed state does double duty as part of another routine.


## Files and checks

* `build.py` generates the design (`python3 build.py fermat.txt`). Test variants:
  `emin` (smaller minimum exponent), `a_init` (A restored with `d` cells, so the
  machine halts iff `x^E + y^E + d = z^E`).
* Shared tools in `../tools/`: `tm.py` parses the format and converts it to
  bbchallenge standard text (`python3 ../tools/tm.py fermat.txt`); `sim.c` is a
  fast simulator (`gcc -O2 -o ../tools/sim ../tools/sim.c`); `minimize.py`,
  `same_run.py`, `greedy_merge.py`, `leangen.py` as below.
* `test_enum.py`: every tuple with total ≤ 34 is visited, none twice.
* `same_run.py A B k`: two machines have identical tapes after 10³..10ᵏ steps
  (used to check each merged machine against the design, up to 10⁸).
* `test_pow.py`: tuples placed directly on the tape (from the setup). Halts on
  3²+4²=5², 5²+12²=13², 7²+24²=25², 1+1=2. Does not halt on 6³+8³ vs 9³ or 9³+10³ vs
  12³. With A offset by `d` cells it halts exactly when `x^E + y^E + d = z^E`, which
  checks the arithmetic exactly; otherwise it returns to the enumeration with the
  tape restored.
* `test_e2e.py`: from a blank tape, the `E >= 1` variant halts on 1+1=2 after 1,546
  steps; with A offset by `d` (10 values) the machine halts on the first tuple of the
  search order with `x^E + y^E + d = z^E`; the real machine (or a given file) runs
  10⁸ steps.

## Formal proof (Lean 4)

`../lean/TinyCryptids/Fermat/` contains a complete, machine-checked proof of

```lean
theorem TM.Fermat.halts_iff :
    Halts delta start ↔ ∃ E x y z : Nat, 3 ≤ E ∧ 1 ≤ x ∧ 1 ≤ y ∧ 1 ≤ z ∧ x ^ E + y ^ E = z ^ E
```

`delta` is the transition table of the 127-state design `fermat.txt` (`Machine.lean` is
generated from that file by `gen_lean.py`), and `start` is the start state on a
blank tape. An undefined transition counts as halting, so the theorem also shows
that no undefined transition is ever reached. The proof uses Lean 4 core only (no
Mathlib), contains no `sorry`, and depends only on `propext`, `Classical.choice`
and `Quot.sound`.

Structure:
* `../lean/TinyCryptids/Core/` (shared by all machines): tapes as streams `Nat → Bool`;
  generic lemmas for single steps, runs of 1s and 0s, and the hole-finding
  parsers; `halts_iff_of_sim` for merged machines. `Tac`: one-step tactics.
* `Copy`, `Pow`: copy loop (with its own cursor), base loop, merge and exponent loop;
  from the anchor with `R = 1` the machine reaches the next-base state with `R = β^E`.
* `NextBase`, `Compare`, `Tuple`: moving the marker and adding R into A, the zig-zag
  (halt iff `x = y + 1`) and its entry, the setup and the clear. `tuple_check` shows that one tuple halts iff
  `a^E + b^E = c^E`, and otherwise returns to the checkpoint.
* `Enum`: the five cases of the next-tuple step, including the transfer loop.
* `Nexcom`: the search order reaches every `(E ≥ 3, a, b, c ≥ 1)` (pure math).
* `Main`: the seed, the main loop, and the theorem.
* `M90`: the generated proof for the merged machine (below).

To check it: install Lean 4.15.0, then `cd ../lean && lake build && lake env lean Check.lean`.
See also `../lean/README.md`.

## Smaller machines

`minimize.py design.txt out.txt K` searches for a merged machine with at most K
states, then K−1, and so on. It only merges states whose transitions agree
wherever both are defined, so the merged machine follows the same run step by
step. The solver matters: `MIN_SOLVER=kissat404` found 90 states within minutes,
where cadical195 stopped at 91; neither had found 89 when the search was stopped.

`gen_reduced_lean.py machines/fermat_90.txt M90` writes `../lean/TinyCryptids/Fermat/M90.lean`:
the merged table, the state map `phi`, a one-case-per-transition check `compat`,
and `TM.Fermat.M90.halts_iff`, derived from `TM.Fermat.halts_iff` through
`halts_iff_of_sim`. Both generators call `../tools/leangen.py`.
`annotate.py` writes the commented listing.
