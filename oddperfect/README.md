# A Turing machine for the odd perfect number conjecture

**Current best: `machines/oddperfect_37.txt`, a 37-state, 2-symbol Turing machine**
(named-state format, as in `../fermat`). Started on a blank tape, it **halts iff
an odd perfect number exists**: it checks n = 1, 3, 5, ... for "sum of the
proper divisors of n = n" and halts at the first odd n that passes. Lean proves
this (`TM.OddPerfect.M37.halts_iff`):

    Halts M37.delta2 M37.start2 ↔ ∃ n, n % 2 = 1 ∧ properDivSum n = n

where `properDivSum n` is the sum of the divisors d of n with d < n
(`TinyCryptids.properDivSum`, `../lean/TinyCryptids/Defs.lean`). `RECORDS.md` lists every machine with its
state count and Lean theorem. `PROOF.md` walks through the proof in plain words.

(A search can only halt when it finds something, so "halts iff an odd perfect
number exists" is the version that does not depend on the answer. A machine
that "halts iff no odd perfect number exists" would need a proof of the
conjecture.)

Bounded searches put any odd perfect number above 10^1500, so the machine
does not halt in any run anyone could watch.

The 37-state machine is obtained in two stages:

1. `oddperfect.txt` is the readable **50-state design** (43 states and a 7-state seed),
   generated by `build.py`. The Lean proof is written for this machine
   (`TM.OddPerfect.halts_iff`).
2. An exact SAT merge of states of the design that never disagree on a transition
   the run uses gives 37 states (`../tools/minimize_clique.py`; 36 is unsatisfiable, so
   37 is optimal for this design). `gen_reduced_lean.py` carries the theorem over to the
   merged machine. `machines/oddperfect_37_annotated.txt` is the same machine with each
   state named after the roles it plays in the design, and every transition commented.

## How it works

Tape layout during the round for n (blocks of 1s separated by `00`):

    T 00 D 00 R

* **D** (d+1 cells, cells 0..d) is the candidate divisor d, **R** (r+1 cells) is
  r = n − d. So D and R together hold n, and moving the separator between them one
  cell to the right steps d → d+1.
* **Holes.** A hole is a single 0 inside a block, used as a counter. 2-state parsers
  ("find the next single 0 to the left/right") do the navigation. A hole may sit next to
  a separator (three 0s in a row) where every parser looking for it comes from the
  right side, as in `../sierpinski`.
* **Divisor test (mod walk, from `../sierpinski`).** D's hole steps cyclically over
  cells 1..d; its *home* is cell d, D's last cell. r times: advance the D hole, then the
  R hole (cells 0..r−1). When the R hole runs off R, the machine runs back over R:
  the first cell left of the separator is D's home, and it is the hole iff d | r,
  i.e. iff d | n.
* **Adding d.** If d | n, the D hole walks down from home to cell 0, one cell per
  step, and each step advances the hole of **T** (n+3 cells), which counts
  u = min(s, n+1), s the sum of the divisors found so far, as a hole at cell u+1.
  Saturation costs no state: when the hole is T's last cell, the step that would move
  it finds the separator, writes the hole back and goes on (`t2` loops on itself).
* **Shift.** d += 1: the first separator cell becomes D's new home, R gives up its
  cell 0 and gets its hole at its new cell 0. When R is then a single cell, r = 0
  and the round is over.
* **Round end.** Six cells are written at the right end (R for the next round),
  D's cell 1 is marked, and the left parser finds the T hole: the two cells after it
  read `1 0` iff the hole is at cell n+1, i.e. iff s = n: **halt**. Otherwise the hole
  is filled, T gets two cells on the left (the new hole at its cell 1), and the right
  parser comes back to the mark: D := 1 with its home on the mark, R := n+1 with its
  hole at cell 0, the round for n+2.

The seed writes `10 00 1`: T for a pseudo-round n = −1 (its hole on its last cell), the
separator and D's first cell. The round end turns this into the end of the round for
n = 1 (an empty round: no candidate), and then the round for n = 3 starts.

What keeps the design small is `../sierpinski`'s mod walk (home on D's last cell: no reset
of the D hole, a 1-state scan back to it), the add loop moving the D hole down instead of a
second cyclic advance, the free saturation of T, and a seed that is a pseudo-round. State budget of the
design: seed 7, mod walk 16, add 8, shift 6, round end 13. After merging, every seed
state is also a step of another routine.

## Files and checks

* `build.py` generates the design (`python3 build.py oddperfect.txt`).
* Shared tools in `../tools/`: `tm.py` parses the format and converts it to
  bbchallenge standard text (`python3 ../tools/tm.py machines/oddperfect_37.txt`); `sim.c` is a fast
  simulator (`gcc -O2 -o ../tools/sim ../tools/sim.c`); `same_run.py A B k`
  checks that two machines have identical tapes after 10^3 .. 10^k steps;
  `minimize_clique.py` (exact SAT, with a maximum clique of pairwise incompatible states
  pinned to distinct classes) and `greedy_merge.py` merge states; `leangen.py`
  writes the generated Lean files.
* `test_e2e.py`: at each round's check (n = −1 .. 341) the tape is compared
  with a Python reference, and the machine runs past 10^8 steps. With `--slow`
  it also runs a test variant that halts iff s > n: it halts at n = 945, the
  first odd abundant number, after about 5.6·10^10 steps.
* `gen_lean.py` writes `../lean/TinyCryptids/OddPerfect/Machine.lean` (the design);
  `gen_reduced_lean.py machines/oddperfect_37.txt M37` writes `M37.lean`;
  `annotate.py`: the readable listing.
* The proof: `../lean/TinyCryptids/OddPerfect/` (see `../lean/README.md`).
