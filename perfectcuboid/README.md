# A Turing machine for the perfect cuboid problem

**Current best: `machines/perfectcuboid_88.txt`, an 88-state, 2-symbol Turing machine**
(named-state format, see `../tools/tm.py`). Started on a blank tape, it **halts iff a perfect
cuboid exists**: a box whose edges, face diagonals and space diagonal are all integers. Lean
proves this (`TM.PerfectCuboid.M88.halts_iff`):

    Halts M88.delta2 M88.start2 ↔
      ∃ a b c d e f g : Nat, 1 ≤ a ∧ 1 ≤ b ∧ 1 ≤ c ∧ a * a + b * b = d * d ∧
        a * a + c * c = e * e ∧ b * b + c * c = f * f ∧ a * a + b * b + c * c = g * g

An *Euler brick* only needs the three face diagonals to be integers; Euler bricks exist (the
smallest is 44, 117, 240), so "halts iff an Euler brick exists" is a solved Σ₁ statement that a
one-state machine satisfies. Whether a perfect cuboid exists is open (none has edges below
about 10¹⁰), so this machine also asks for the space diagonal `g`.

The 88-state machine is obtained in two stages:

1. `perfectcuboid.txt` is the readable **154-state design**, generated by `build.py`. The Lean
   proof is written for this machine (`TM.PerfectCuboid.halts_iff`).
2. `../tools/minimize_clique.py` merges states of the design that never disagree on a
   transition the run uses. 88 is optimal for this design (a clique of 87 pairwise
   incompatible states, 87 classes UNSAT). `gen_reduced_lean.py` carries the theorem over, and
   `machines/perfectcuboid_88_annotated.txt` is the same machine with each state named after
   its roles in the design.

## The idea: squares without multiplication

`N` is a square iff it is `1 + 3 + 5 + …` exactly. A counter **S** counts units and tells whether
the count is a square; each edge block **X** of `L` cells feeds S exactly `v²` units, `v = L/2 − 1`,
because inside X a region of 1, 3, 5, …, `2v − 1` cells is cycled through by a hole. So the sum of
the squares of any run of blocks can be tested by resetting S, running the blocks and looking
at S.

To test the four sums `a² + b²`, `a² + c²`, `b² + c²`, `a² + b² + c²` with one counter, the blocks
run cyclically through the queue `A B C Z` (Z a block worth 0) and S is reset after every third
block: the windows between resets are `[A B C] [Z A B] [C Z A] [B C Z]`. S is checked after every
block (the single squares and 0 always pass); the four checks that can fail are exactly the four
sums. A window counter W (a marker in the gap before S) decides the resets.

## How it works

The tape, left to right (blocks of 1s separated by `00`; a hole is a single 0 inside a block):

    A 00 B 00 C 00 Z  G  S

* **A, B, C**: blocks of `L ≥ 4` cells, the edges `v(L) = L/2 − 1`.
* **Z** = `111`, worth 0.
* **G**: eight cells, the window counter: `00000000` (W = 0), `00001100` (W = 1), `00110000` (W = 2).
* **S**: a leading 1, `2k + 1` cycle cells with one hole, a terminator 1. The hole on cycle cell
  `j` stands for `N = k² + j`; N is a square iff `j = 0` (home). A step moves the hole one cell;
  past the last cell it goes home and S grows by two cells.

**A block.** Once set up, X has its hole `h` on its last cell (home) and a mark `m` on cell
`L − 3`; the region is `m + 2 … L − 1`. One unit: `h` moves one cell on in its region (from home
back to the region's first cell), then the head goes to S, makes one step and comes back to `h`.
When `h` arrives home its region is used up and `m` moves two cells left (the region grows by
two); when `m` cannot move the block is done after its last unit. So X gives
`1 + 3 + … + (2v − 1) = v²` units.

**Between blocks.** The next block Y is set up (`h`, `m`; for Z only `h`), then the head goes to S:
the hole home means a square and W ticks (`0 → 1 → 2 → 0`; on the wrap S is reset to `101`), then
back to Y's `h` and Y is processed. After Z the head finds G: W = 2 there means the fourth window
has passed: **halt**; otherwise home to A.

**Not a square: the next tuple.** S's hole goes home (the next tuple's first check passes and its
tick resets S), W := 2, the head scans home filling the holes of Y on the way, and NEXCOM
(Nijenhuis–Wilf's order of compositions, each part at least 4 cells, A with the free end on the
left) makes the next `(A, B, C)`: `(x − 1, y + 1, z)` if `x > 4`, else `(y − 1, 4, z + 1)` if `y > 4`, else
`(z + 1, 4, 4)`, by merging blocks and cutting them again at fixed offsets. Every length triple
`≥ 4` comes up (`Spec.reached`), so every `(a, b, c) ≥ 1` does (as `(2a + 2, 2b + 2, 2c + 2)`).

**Start.** The seed writes S's `101` and enters the abort routine, which writes G; its scan finds
no queue, NEXCOM's entry reads a blank there, and a chain writes Z and `(4, 4, 4)`.

## Files and checks

* `build.py` generates the design (`python3 build.py perfectcuboid.txt`); its docstring describes the
  tape.
* `test_model.py`: from a blank tape, every square check of the design (state `k3`) agrees with an
  abstract model of the windows, and the tuples follow `nxt`.
* `test_windows.py`: hand-placed tuples. The Euler brick `(44, 117, 240)` started in the second,
  third or fourth window halts (the remaining windows only test face diagonals); started in the
  first window it goes on to the next tuple, since `44² + 117² + 240² = 73225` is not a square (`270² = 72900`, `271² = 73441`);
  tuples with one edge changed go on too. Odd block lengths give the same values.
* `test_e2e.py`: both machines run 10⁸ steps from blank without halting, plus the two tests above.
* `../tools/same_run.py perfectcuboid.txt machines/perfectcuboid_88.txt 9`: the same tapes up to 10⁹ steps.
* `gen_lean.py` writes `../lean/TinyCryptids/PerfectCuboid/Machine.lean`;
  `gen_reduced_lean.py machines/perfectcuboid_88.txt M88` writes `M88.lean`; `annotate.py` the listing.
* `classes.py design merged`: which design states each merged state plays (the singletons).
* The proof: `../lean/TinyCryptids/PerfectCuboid/`, see `PROOF.md`.
